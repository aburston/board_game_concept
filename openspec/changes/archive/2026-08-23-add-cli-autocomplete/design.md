## Context

Three facts about the current code decide most of this design.

The first is how a line is read. `session.read_command` prints the prompt
itself with `print(f"{prompt}> ", flush=True, end='')` and then calls
`sys.stdin.readline()`. That is deliberate — the docstring records why: `input()`
raising `EOFError` and `readline()` returning `''` were confused with a blank
line once already, and the whole CLI test suite drives roles through pipes and
asserts on prompt counts in the captured output. Completion, however, is a
`readline` feature, and `readline` only participates when input is read through
`input()` on a terminal. So the read has to fork on whether it is talking to a
person, and the branch that is not talking to a person must stay exactly as it
is.

The second is that `grammar.py` already exists and already states its purpose:
one description of the language, so `help` cannot drift from the parser. It
describes each command as a display string — `'move <unit> <north|east|south|west>'`
— which a person can read and nothing can compute with. Completion needs the
same commands as words and slots. Writing that as a second table would recreate
exactly the drift `grammar.py` was made to prevent, so the structured form
becomes the definition and the display string is generated from it.

The third is that a role's `Game` already holds only what that role may see —
a client is loaded from its own published view — and `views.py` already turns
it into plain data with stable names. Completing a unit name is therefore not a
new read of the game; it is a filter over `units_view(data.getBoard())`.

## Goals / Non-Goals

**Goals:**

- Tab completes every fixed word of the grammar, at the position it belongs.
- Tab completes the names the player is going to type next that only the game
  knows: their own units, their own types, and paths on disk.
- One description of the language behind the parser, `help`, and completion,
  and one table deciding what a role may do behind both the refusal and the
  offer.
- Non-interactive sessions byte-for-byte as they are today, proven by the
  existing suite passing untouched.
- Shell completion for the arguments the three commands are launched with.

**Non-Goals:**

- Replacing the parser or the session loop with `cmd.Cmd`. It would take over
  the loop, the prompt, the help and the dispatch, and this project has a
  parser it likes with a grammar it generates help from.
- A history file that outlives the session. Within-session history comes free
  with `readline`; a file is a separate decision about where to write and what
  to leak between games.
- Completing numbers, or inventing names for things that do not exist yet.
  `add type <name>` is the player naming something; a suggestion there would be
  a guess.
- Ctrl-C behaviour, colour, prompt styling, or a right-hand hint line.
- Validating as you type. Completion offers; the parser still judges.

## Decisions

### The grammar table becomes structured, and generates its own usage strings

Each `Usage` is defined by its words rather than by a sentence:

```python
Usage('move', ('move', Slot('unit', UNIT), Slot('direction', DIRECTION)),
      'order one of your units to move')
```

A word is either a literal string, a `Slot(display, kind)`, or an
`Optional('json')`. `Usage.usage` — the string `help` prints — is generated by
joining them: a literal as itself, a slot as `<display>`, an optional as
`[json]`. The `move` usage still prints
`move <unit> <north|east|south|west>` because the direction slot's display name
is built from `DIRECTIONS`, as it is today.

This keeps one description of the language, which is the file's stated reason
for existing. The alternative — a `COMPLETIONS` dict beside `USAGES` — is two
descriptions of one grammar, and the second one goes stale the first time a
command changes.

Slot kinds are a small closed set: `UNIT`, `TYPE`, `PATH`, `DIRECTION`,
`NUMBER`, `NAME`, `SYMBOL`. Only the first four have candidates; `NUMBER`,
`NAME` and `SYMBOL` complete to nothing, which is the honest answer for a
coordinate or a name being invented.

The parser is not rewritten to walk the table. Its recursive-descent methods
carry the error messages the specs name word for word (`must provide 5 args for
type`), and a table-driven parser would have to reproduce them. The table
describes the shapes; the parser keeps the diagnostics. They are checked against
each other by a test that every `Usage` parses as its own kind when its slots
are filled with plausible words.

### One predicate for "does this role offer this usage"

`help.py` already filters `USAGES` by `usage.kind in role.kinds` and
`usage.subject in role.show_subjects`. Completion needs the same filter, so it
moves onto `Role` as `role.offers(usage)` and `help.py` calls it. That is what
makes the spec's "the offer matches the refusal" true by construction rather
than by two lists agreeing: `allows()` and `offers()` read the same two frozen
sets.

### Completion as a pure function, with `readline` a thin shell around it

`cli/complete.py` holds:

```python
def candidates(line, role, source):
    """The words that could come next, given everything typed before the cursor."""
```

`line` is the text left of the cursor, `role` is the role's table, and `source`
is where live names come from. It splits the line, decides whether the last
word is being completed or a new word is starting (the line ending in a space),
then walks each usage the role offers: literals must match the words already
typed, slots consume one word each, and the first usage element past the typed
words contributes its candidates. Results are unioned across usages, filtered by
the prefix, deduplicated and sorted.

Being a pure function of a string is what makes this testable without a
terminal: `tests/test_completion.py` calls `candidates('show ', CLIENT, ...)`
and asserts on a list. The `readline` shell around it is the only part that
needs a pty, and it is a dozen lines.

The `readline` callback receives only the current word, not the line, so the
callback reads `readline.get_line_buffer()[:readline.get_endidx()]` and passes
that. It caches the list on `state == 0` and indexes it afterwards, as
`readline` callbacks must.

Delimiters are set to whitespace only — `readline.set_completer_delims(' \t\n')`.
The default set includes `/`, which would make `games/bo` complete as the word
`bo` and paste the completion over the directory. Whitespace-only delimiters are
also what make a path one word, as the spec requires.

`libedit` (what `readline` is on macOS) needs `bind ^I rl_complete` rather than
`tab: complete`; both are bound, chosen by looking at `readline.__doc__`. The
whole import is guarded: if `readline` will not import, `install()` returns
having done nothing, and the session runs without completion. That is a real
case on Windows, and the spec says it must be silent.

### Live names come from a source object, not from the game directly

The completer is handed a `source` with two methods, `units()` and `types()`,
so `complete.py` does not know what a `Game` is and the tests do not need one:

```python
class GameNames:
    def __init__(self, data, player_number): ...
    def units(self):  # own units, in play, not destroyed
    def types(self):  # own type names
```

Both are built from `views.units_view(...)` and `views.types_view(...)` and
filtered on `player`. Reusing the views rather than walking `board.units`
directly means the names completion offers are the names `show units` prints —
including the fact that a destroyed unit's state reads `destroyed`, which is the
filter that keeps it out.

The source holds the same `Game` object the session loop holds, so a unit
deployed a moment ago is already in it. Nothing in the source calls `load()`,
`save()` or the repository — the spec forbids it, and reading disk on every
keystroke would be felt.

Each role builds its own source. The server and observer are player 0 and hold
neither `move` nor `add unit`, so their sources answer nothing; they still get
path completion, which is what `load board` and `load player` need.

### Paths are completed by the completer, not by `readline`

`readline` has a filename completer, but it is engaged for the whole line, not
for one slot. The `PATH` slot is completed with `glob.glob(prefix + '*')`
instead, appending `/` to directories so the next Tab descends. That keeps one
completion function answering for every position, which is what the tests
assert on.

### Reading a line: fork on the terminal, not on a flag

```python
if sys.stdin.isatty() and sys.stdout.isatty():
    try:
        line = input(f"{prompt}> ")
    except EOFError:
        print()
        return commands.Exit()
else:
    print(f"{prompt}> ", flush=True, end='')
    line = sys.stdin.readline()
    ...unchanged...
```

Both conditions are checked: `readline` writes its prompt and its redraws to
stdout, so a session with a terminal on stdin and a pipe on stdout must take
the plain path or the captured output grows escape sequences. The EOF branch
prints the same blank line the current code does, so a person pressing Ctrl-D
sees the same thing.

`input()` is used rather than `readline` being told to decorate
`sys.stdin.readline()` because `input()` is the only call the `readline` module
hooks. This is the exact confusion the existing docstring warns about, so the
docstring is extended rather than replaced: `EOFError` here, `''` there, both
meaning `exit`.

### Shell completion ships as files to source

`completions/bgc.bash` and `completions/bgc.zsh`, plus a README section saying
to source them or drop them in the shell's completion directory. Game numbers
come from `games/_*` in the current directory with the `_` stripped; player
numbers for `bgcclient`'s second argument come from `games/_<gameno>/players/<n>.yaml`,
which is where the repository writes them. Both are a `compgen -W` over a
directory listing — no Python is run to answer a completion.

Not chosen: `argcomplete`, which would add a runtime dependency to a project
whose only one is PyYAML, and only completes `argparse` — which is one flag on
one of the three roles. Also not chosen: installing the scripts into
`/etc/bash_completion.d` or `~/.local/share/bash-completion` from `pip install`.
There is no portable place to put them, `pip` should not write outside its
prefix, and `cli-installation` says installing the package installs the three
commands and nothing else. Files plus a documented line to source is the honest
version.

### Testing without a terminal, and once with one

`tests/test_completion.py` tests `candidates()` directly: every position of
every command for each of the three roles, the role filter (the observer is not
offered `move`; the client is not offered `show pending`), names from a small
built game, another player's unit excluded, a destroyed unit excluded, and path
completion in a temporary directory.

One pty test drives a real `bgcclient` through `pty.openpty()`, sends `sh\t`,
and asserts the terminal shows `show`. It is skipped when a pty cannot be
allocated. It is the only evidence that the wiring — delimiters, key binding,
the callback — is right, and everything else is testable without it.

The existing CLI surface suites are the regression evidence for piped input and
must pass unchanged. A test asserting the captured output of a piped session
holds no `\x1b` makes that explicit rather than incidental.

## Risks / Trade-offs

- **Switching the interactive read to `input()` changes prompt handling on the
  terminal path.** → The piped path is untouched and the suite that drives it
  is untouched. The terminal path is covered by the pty test, and `input()`
  writing the prompt is what lets `readline` redraw it correctly when a line is
  edited.
- **`readline` is not available everywhere, and is `libedit` on macOS.** →
  Guarded import, both key bindings, and a spec scenario for the session running
  without it.
- **Structuring `USAGES` touches the file `help` is generated from.** → The
  generated strings are asserted against the current `help` output for each
  role, so the change is provably invisible in what `help` prints.
- **Completion could offer a name the command then refuses** — a unit with no
  energy to move, a type after setup has closed. → Completion answers "what
  words fit here", not "would this be allowed now". The service layer still
  judges; offering a name is not a promise. Stated in the spec as offering only
  a valid continuation of the *line*.
- **A very large game makes completion slow.** → Candidates are built from
  views over the units in memory; a board game's worth of units is tens of
  entries.
- **The shell scripts duplicate knowledge of the storage layout** (`games/_*`,
  `players/<n>.yaml`). → It is two globs, and `cli-installation` already fixes
  `games/_<gameno>` as the contract between a game number and the disk. A test
  reads the scripts and checks the paths they glob still match what the
  repository writes.

## Open Questions

None. Scope was settled with the user: completion of the grammar *and* of live
game data, in-session, plus shell completion for launching the commands.
